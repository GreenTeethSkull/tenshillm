# Chat History and Streaming State Hardening

## Goal

Preserve existing chat history while making assistant message lifecycle explicit
and ensuring partial or failed responses are never sent back as provider history.
The visible streamed assistant message remains the same message that is stored;
there is no second content-only rendering path.

## Scope

- Migrate the previous generated Thinking markup in persisted assistant messages.
- Track assistant completion state for streaming, completion, cancellation, and errors.
- Exclude non-complete assistant messages from OpenAI-compatible payloads.
- Remove the transient `streamingContent` mirror and synthetic streaming message.
- Keep provider reasoning as presentation metadata only.

## Message Lifecycle

Add an optional `completionStatus` field to `Message` with these values:

- `streaming`: the assistant response is currently being received.
- `complete`: the response can be used as provider history.
- `aborted`: generation was cancelled before completion.
- `error`: generation failed before completion.

Only assistant messages use this field. Existing persisted messages without the
field are treated as `complete`, preserving compatibility. New assistant
messages start as `streaming`, become `complete` after `requestCompletion`
returns successfully, and become `aborted` or `error` on the corresponding exit
paths.

## Persistence Migration

Move legacy message conversion into a pure chat-history helper. The Zustand chat
persist version increases from 1 to 2 and its migration converts the exact
wrapper previously generated by `buildDisplayContent`:

```text
<details><summary>Thinking</summary>

{reasoning}

</details>

{answer}
```

The migration stores `{reasoning, answer}` separately and leaves unrelated
assistant content unchanged. The UI renderer will not contain persistence or
legacy-format knowledge.

## Provider History Boundary

`buildChatPayload` remains the canonical provider projection. While iterating
stored messages, it skips assistant messages whose explicit status is not
`complete`. Messages without a status are treated as complete for old data.
Reasoning is never included in provider messages; only clean assistant content
is sent.

## Streaming Rendering

Remove `streamingContent` and `setStreamingContent` from the chat store and
delete the synthetic fallback `MessageBubble`. `ChatView` renders the assistant
message already present in `currentMessages`, passing `isStreaming` only when
the request is active and that message has `completionStatus: 'streaming'`.

The global `isStreaming` flag remains the request-level state used by the input
and stop control. It no longer stores a second copy of response content. Scroll
updates depend on `currentMessages`, which changes whenever the real assistant
message receives a stream update.

## Error and Cancellation Handling

Cancellation marks the active assistant message as `aborted` before cleanup.
Non-cancellation failures mark it as `error` and retain the visible diagnostic.
Both states remain visible locally but are filtered from subsequent provider
history.

## Verification

- Unit-test legacy persistence migration and preservation of unrelated messages.
- Unit-test provider payload filtering for legacy, complete, streaming, aborted,
  and error assistant messages.
- Keep existing normalization and stream parser tests.
- Run `bun run test`, `bun run build`, and `bun run lint`.
- Inspect the final diff for accidental persistence of transient UI state.

## Acceptance Criteria

- Existing chats with old Thinking markup render as a native collapsed section.
- A stopped or failed assistant response remains visible but is not sent in the
  next provider request.
- Only one rendered message owns streamed content and reasoning.
- Completed tool-call assistant messages remain in protocol order.
- New messages continue to store clean `content` and separate `reasoning`.
